# Estimate Cost — ศึกษาและปรับปรุงจากของเดิม

สถานะ: Draft · ปรับตามคำชี้แจงผู้ใช้ 7 กันยายน 2026 · ขอบเขต: ศึกษา UX เดิมและเสนอแก้เฉพาะจุด

เอกสารนี้ขยาย [DESIGN.md](../DESIGN.md) สำหรับ Estimate Cost ผู้ใช้กำหนดให้ศึกษาการใช้งานเดิมก่อน ไม่ออกแบบหน้าทดแทนทั้งหมด ข้อเสนอก่อนหน้าที่รวมแท็บเหลือ 4 กลุ่ม ย้าย Validation ไปแผงข้าง ซ่อนยอดแยก และเปลี่ยนฟอร์มเป็น drawer ถูกถอนออกจากขอบเขตปัจจุบัน ยังไม่มีการเปลี่ยน UI ตามข้อเสนอเหล่านั้น

## ประเด็นที่มีหลักฐานให้ตรวจต่อ

### 1. แถวเพิ่มด่วนอาจถูกทิ้งเมื่อเปลี่ยนหมวด

ใน `EstimateCostItemsTab` ปุ่ม discipline เรียก `setQuickDraft(null)` และ Escape ล้างร่างโดยตรง จึงมีเส้นทางที่อาจทำค่าที่กรอกหาย ต้องทดสอบด้วยแถวที่กรอกแล้วแต่ยังไม่บันทึกก่อนแก้

ข้อเสนอเฉพาะจุด: เมื่อมีค่าร่างที่เปลี่ยนจริง ให้ยืนยันก่อนทิ้งข้อมูล ใช้พฤติกรรมเดียวกับการยกเลิก/ออกจาก editor; แถวว่างไม่ควรถูกถามซ้ำ รักษา Enter บันทึกและเพิ่มต่อ และการพิมพ์ผ่าน IME

### 2. จำนวนคำเตือนใช้ฐานคนละชุด

ยอด Validation มาจาก `workspace.validationIssues` แต่ป้าย `to fix` ในโมดูลมาจาก `costModuleGroups`: นับราคาที่ไม่เกินศูนย์ หรือกรณีมีราคาแล้วแต่ไม่มีผู้ขายในหมวดวัสดุ ทั้งสองยอดจึงไม่จำเป็นต้องตรงกัน และยังไม่ใช่หลักฐานว่า validation คำนวณผิด

ข้อเสนอเฉพาะจุด: ปรับป้ายและคำอธิบายให้อ่านออกว่าอันไหนเป็นผลตรวจเอกสาร อันไหนเป็นรายการรอข้อมูล โดยคงตรรกะและระดับ blocking/advisory เดิม ไม่เพิ่มเงื่อนไขบล็อกหรือเปลี่ยนฐานนับโดยอัตโนมัติ

### 3. Approved ยังเห็นแถว Add item ที่ disabled

`add-row` ยังคง render และ disabled เมื่อ `canAdd` เป็น false ตามภาพที่ผู้ใช้ส่ง

ข้อเสนอเฉพาะจุด: ทำเหตุผลอ่านอย่างเดียวให้ชัด ณ บริเวณตาราง อาจซ่อนเฉพาะแถวเพิ่มที่ใช้งานไม่ได้ใน Approved/Locked หลังตรวจว่าผู้ใช้ยังเห็นเหตุผลและ Create Revision ได้ตามสิทธิ์ ไม่ย้ายเครื่องมือทั้งหน้า ไม่ทำให้บัญชีที่มีสิทธิ์แก้เฉพาะหมวดสูญเสียปุ่มที่ใช้งานได้

### 4. พื้นที่เหนือรายการและการตัดข้อความ

ภาพแสดงข้อมูลเหนือรายการหลายส่วน แต่ยังไม่มีหลักฐานว่าผู้ใช้ต้องการลดข้อมูลหรือเปลี่ยนแท็บ

ข้อเสนอเฉพาะจุด: วัดภาพที่ขนาดจอใช้งานจริง เปรียบเทียบระยะห่าง ความสูงส่วนหัว ชื่อโมดูล/สินค้า และคอลัมน์ตรึงก่อนเสนอปรับ spacing เฉพาะ Estimate ไม่กำหนดว่าต้องยุบส่วนสรุปหรือให้เห็นจำนวนแถวตายตัว

## ลำดับศึกษาก่อนแก้หน้าจอ

1. เปิดตัวอย่าง Draft และ Approved เดิมโดยไม่เปลี่ยนข้อมูลธุรกิจ จดว่าแต่ละบทบาทเห็นปุ่มใดและใช้ทำอะไร
2. ตรวจเส้นทางเพิ่มด่วน → บันทึก/ยกเลิก, แก้รายละเอียด, เปลี่ยนหมวด, พับโมดูล และ Compact/All columns โดยใช้ fixture หรือข้อมูลทดสอบสำหรับขั้นตอนเขียน
3. ตรวจ Engineering Man-hour, ค่าใช้จ่ายอื่น และการแยกยอด เพื่อไม่ออกแบบจาก Cost Items แท็บเดียวแล้วกระทบทั้ง Estimate
4. ตรวจ Validation → ตำแหน่งที่แก้, Assignment, Submit/Approve/Request Revision/Create Revision โดยอ้างอิง regression เดิม และใช้ฐานทดสอบแยกเมื่อจำเป็น
5. ตรวจ Excel และ Template ตั้งแต่เปิดตัวเลือกถึง Preview ไม่ยืนยันนำเข้าข้อมูลจริงเพื่อทดลอง UX
6. สรุปแต่ละประเด็นเป็น “ของเดิมทำอะไร / มีปัญหาตรงไหน / จะแก้เฉพาะอะไร / อะไรคงเดิม” แล้วจึงดำเนินการแก้จุดที่มีหลักฐาน

## ขอบเขต implementation และเกณฑ์รับงาน

- รอบนี้ปรับเอกสารให้ตรงเจตนาผู้ใช้ ยังไม่มีการแก้หน้าจอหรือ restart ระบบ
- คงแท็บ 9 อัน ตาราง ปุ่มหลัก ฟอร์มเดิม คอลัมน์และยอดที่แสดงเป็นค่าเริ่มต้น; ไม่สร้าง navigation หรือ design system ใหม่
- ยอดจาก SQL, contingency, man-day/rate, immutable revisions, row versions, section-level permissions, Excel export/import transactions และ provenance ต้องคงเดิม
- ใช้ components, CSS tokens และ TH/EN/JP เดิม ชื่อบริษัท/รหัส/ข้อความผู้ใช้/canonical API values ไม่ถูกแปล
- ปรับเฉพาะปัญหาที่ตรวจพบ ไม่เพิ่ม search/filter/drawer/autosave เป็นส่วนจำเป็นของรอบนี้ ฟีเจอร์ใหม่ต้องมีเหตุผลการใช้งานแยกจากการแก้ UX เดิม
- ก่อนแก้พฤติกรรมร่าง ให้เพิ่ม regression ที่ทำปัญหาซ้ำได้ ตรวจ save/cancel/navigation/IME/error และสิทธิ์ที่ต่างกัน
- ใช้ `tests/cost-item-validation.test.mjs`, `tests/production-guardrails.test.mjs`, `tests/estimate-create-revision-contract.test.mjs`, `tests/estimate-excel-import.test.mjs` ตามส่วนที่เปลี่ยน ตามด้วย typecheck/lint/build ที่เกี่ยวข้อง
- การเปลี่ยน spacing ต้องมีภาพก่อน/หลังในสถานะเดียวกันที่ desktop และจอแคบ รวม TH/EN/JP, keyboard focus และ 200% zoom เป้าหมาย accessibility คือ WCAG 2.2 AA ไม่ใช่ผลรับรองว่าผ่านแล้ว
