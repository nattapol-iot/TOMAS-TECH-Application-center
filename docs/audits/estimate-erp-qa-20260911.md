## Blockers

### Blocker 1 — no Team Test credential is available to this session (blocks scenarios 1b, 2, 3b, 3f live)

The API runs in `Authentication__Mode=TeamTest` and authenticates per request on the `x-team-test-email` / `x-team-test-code` headers, where the code is derived from the runtime signing key (`backend-node/src/auth.ts:33-41`). The task supplied no account, and the launcher reads the signing key from a DPAPI-protected local store (`scripts/Start-LocalReadOnlyApi.ps1:41`). Reading that key to mint an access code would be issuing myself a credential, which this assignment forbids, so it was not attempted and nothing was read from the secrets store.

Guard behaviour was confirmed instead, with no real secret used: unauthenticated and malformed-credential requests are rejected 401 with distinct codes and no stack trace or server error (`01-http-auth-guards.txt`).

**To unblock, one of:** (a) an operator issues a QA access code for a disposable Team Test account via `scripts/New-TeamTestAccessCode.ps1` and hands over the email plus code out of band; or (b) an authenticated browser session is made available for UI testing. With either, scenarios 2, 3b and 3f can be completed against `TEST-ERP-QA-20260911` records in one pass.

### Blocker 2 — company ERP import is out of scope and unverified

No access to the company ERP was requested or attempted. Nothing in this report asserts that an import into the ERP succeeds. Only the workbook hand-off artefact was verified.

## What passed, with the evidence

**Health.** `GET /health/live` → `200 {"status":"ok"}`; `GET /health/ready` → `200 {"status":"ready","schemaVersion":43,"documentStorage":"available"}`. The `/api/v1/health/*` paths do not exist; health is unprefixed. Frontend `GET /` → `200`.

**Seven categories and five source ledger types (3a).** A synthetic estimate covering `CostItem`, `ManhourLine`, `ExpenseLine`, `OtherCostLine` and `Contingency` maps into all seven ERP categories with correct per-category amounts and line counts (`S3.1`, `S3.2`). A contingency below 0.005 is dropped from the line set rather than shown as a zero row (`S3.9`).

**Reconciliation (3c).** `classifiedTotal + unmapped + overhead == canonicalTotal`, tolerance exactly ±0.01 — 0.010 reconciles, 0.011 does not (`S3.3`, `S3.7`, `S3.8`).

This identity is structurally sound, not just true for the fixture. `dbo.v_estimate_totals` (migration 040) computes `total = base_total + overhead_total + contingency`, where `base_total` buckets *every* non-deleted ledger row: `cost_items` across all ten codes permitted by `CK_cost_items_category_code` (01–05 material, 06/10 other, 07 outsource, 08 transportation, 09 accommodation), all `manhour_lines.line_cost`, and `expense_lines` / `other_cost_lines` with catch-all `NOT IN` buckets. The ERP query lists exactly the same rows. No row can appear in one total and not the other, and overhead enters once. All four line totals are `PERSISTED` computed columns (`qty * unit_cost`, and `engineers * man_days * daily_rate`), which is why the workbook's "total must equal unit price × quantity" row check cannot false-block on real data.

**Unmapped guard (3d), two independent layers.** Server: `capabilities.canExport` is false whenever any line is `Unmapped`, and `POST /erp-export-events` refuses with `409 estimate_erp_export_blocked` (`S3.4`, route logic). Client: `buildErpEstimateWorkbook` throws before producing bytes (`S4.2`). Overhead state `Missing` blocks export, `Zero` and `Applied` permit it (`S3.5`, `S3.6`, `S4.3`) — the server rule (`state !== "Missing"`) and the client rule (`state === "Applied" || "Zero"`) are equivalent because migration 040 defines exactly those three states.

**Unsaved-changes guard (3e), two independent layers.** The export button is disabled while `changedLines.length > 0` with the message "Save mapping changes before export." (`EstimateErpSummary.tsx:166,169`, present in the served bundle). Independently, saving mappings touches `dbo.estimates`, which bumps `row_version`, so a stale export event is rejected `409 concurrency_conflict` by the row-version check in the export route.

**Mapping input guards.** Invalid category (including the string `Profit`), unknown source type, duplicate source, a `Contingency` carrying a source id, and batches outside 1–500 are all rejected with specific messages; `Unmapped` is accepted as a target so a mapping can be cleared (`S3.11`–`S3.16`).

**Export-event guards.** Wrong template version, mismatched SHA-256, a filename with a path separator, a non-`.xlsx` extension and a payload that is not a ZIP package are each rejected; the real generated workbook and its checksum are accepted (`S4.10`, `S4.11`).

**Revision and approval restrictions (3f, code review only).** Mappings are editable only in `Draft`, `Engineering Input`, `Engineering Review`, `Revision Required` (otherwise `409 estimate_locked`) and only by the owner, an Engineering Manager or an Admin (otherwise `403 estimate_owner_required`), under `UPDLOCK, HOLDLOCK` with a row-version check. Creating a revision copies every mapping for all five source types with `copied_from_mapping_id` / `copied_from_revision` provenance (`backend-node/src/routes/estimates.ts:197-216`), and `materializeErpMappings` back-fills defaults (`01`→Hardware, `02`→Software, `Installation` man-hours→Installation, everything else→Unmapped). **None of this was executed** — it needs a credential and a database.

**Export scale.** Generated packages stay far below the server's 650,000-byte ceiling: 1,000 lines → 49 KB, 6,000 lines → 270 KB. The cap is roughly 14,000 lines; no realistic estimate can hit it (`06-export-limits.txt`).

**No commercial figures.** The generated sheet contains no profit, margin, markup or selling price. The reference workbook carries a `Profit` row at 30 % (`K52=0.3`, `L52=871,181.40`) inside its Grand Total; the app deliberately omits it and totals `Sub Total + Approved Overhead = Grand Total` only. **This divergence is correct and must not be "fixed".**

## Defects

All four are in the Excel export format (scenario 4b). Severity is the impact on the person receiving the file; none corrupts data.

### D1 — Medium — printed output does not fit the page; the fit-to-width setting is inert

`lib/erp-estimate-workbook.ts:217` emits `<pageSetup orientation="landscape" fitToWidth="1" fitToHeight="0"/>` but the worksheet has no `<sheetPr><pageSetUpPr fitToPage="1"/></sheetPr>`. Per ECMA-376, `fitToWidth`/`fitToHeight` are ignored unless `fitToPage` is set, so Excel prints at 100 % scale. The sheet is 15 columns wide with column E at 109.6 characters, so a real estimate prints across many pages with columns split across sheets. The reference solves this with `paperSize="9" scale="20" orientation="portrait"` — A4 at 20 %.

*Reproduce:* open `.omx/artifacts/estimate-erp-qa/TEST-ERP-QA-20260911_R02_ERP_EstimateCost.xlsx` → File → Print, or inspect `xl/worksheets/sheet1.xml`; compare with the reference's `sheet1.xml` (both decoded in artifacts 03 and 05).

*Fix:* add `<sheetPr><pageSetUpPr fitToPage="1"/></sheetPr>` as the first child of `<worksheet>`, or match the reference exactly with `paperSize="9" scale="20" orientation="portrait"`. Print margins also differ (0.25/0.5 vs the reference's 0.7/0.75) — cosmetic, fix alongside.

### D2 — Low — the Item column mixes item codes with a partial running number

`worksheetRows` writes `row.item ?? sequence++`, and the counter advances only when `item` is absent. In the generated sheet that produces `HW-001`, `SW-001`, `Engineering design`, then bare `1`, `2`, `3` on rows 17, 26 and 29. The reference's Item column is a pure running number (`=ROW()-8`, 1…42) with the part number in column D. The result reads as a numbering error to whoever receives the file.

*Reproduce:* artifact 05, rows r10/r13/r16/r17/r26/r29. Any estimate with a mix of coded and uncoded lines shows it.

*Fix:* either always emit a running sequence in the Item column and move the item code to the Model/Part Number column, or always emit the code and leave the cell blank when there is none. Do not mix.

### D3 — Low — the export date is written as text, not a date

`L3` is the inline string `2026-09-11`; the reference holds the serial `46254` with a date format. Excel left-aligns it, will not reformat it to the recipient's locale, and cannot sort or filter on it.

*Fix:* write the serial date with a `numFmt`, as the reference does.

### D4 — Low — the workbook is a snapshot of values with no formulas

Every amount, subtotal, `Sub Total`, `Approved Overhead` and `Grand Total` is a literal. The reference uses `=J9*K9` per line and `=SUM(L9:L50)` / `=SUM(L51:L53)` for the totals, so a reviewer can see and re-check the arithmetic in Excel. Static values are defensible for a controlled export, but the receiving side loses the ability to audit or extend the sheet.

*Fix, if the business wants parity:* emit `=J{r}*K{r}` on line rows and `SUM` on the subtotal, Sub Total and Grand Total rows, keeping the cached value so nothing depends on recalculation.

## Observations (not defects)

- **The exported bytes are not reproducible across runs.** Identical input produced `e05662e3…`, `38c2714e…` and `812ad509…` in three runs, always 4,207 bytes; the ZIP embeds the build clock. Two exports of an unchanged estimate therefore carry different SHA-256 values in the audit trail. Impact is limited because the same audit row also stores `mappingDigest`, a deterministic hash of the mapping and amounts, which is the field to compare when asking "did the content change?".
- **The export event uploads the workbook, then discards it.** `POST /erp-export-events` accepts up to 650 KB of base64, verifies the checksum, and writes only an audit row — the bytes are never stored, unlike `unified_report_exports`, which archives generated files. Nobody can retrieve the exact file that was exported later, only its checksum. Either archive it or stop uploading it.
- **The audit entry is written before the download happens.** `EstimateErpSummary.tsx:125-132` awaits `recordEstimateErpExport` and only then triggers the browser download, so a blocked or failed download still leaves an "ERP Summary exported" audit entry.
- **The two overhead gates are equivalent only by coincidence of today's state list.** Server: `overhead_state !== "Missing"`. Client: `"Applied" || "Zero"`. Migration 040 emits exactly those three states, so they agree; a fourth state added later would be exportable server-side and blocked client-side without any test failing.
- **The header labels reproduce the reference's original spellings** — `Custumer`, `Shot name`, `Discription`, `Suppier`, `Discription/Detial`, `Total (BATH)`. These match the Okaya x SSSC file exactly and are deliberate fidelity, not typos to fix.
- **Layout differences from the reference that are improvements, not defects:** the app emits a merged section header row per ERP category plus a `<Category> Sub Total` row (the reference labels the group in column D of its first row and has no per-group subtotal), and adds a frozen header pane and an autofilter on `C8:N8`. Column widths C–O, the header block rows 1–6 and the column header row 8 match the reference exactly, as does the print-area pattern `'Summary cost'!$C$1:$O$n`.
