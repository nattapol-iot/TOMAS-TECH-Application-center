# ศูนย์แจ้งปัญหา — Support Center

สถานะ: ข้อเสนอการออกแบบวันที่ 6 กันยายน 2026 — เพิ่มฟีเจอร์ในแอปจริงแล้วตามคำสั่งผู้ใช้ ดูขอบเขตที่ส่งมอบและผลตรวจสอบใน [รายละเอียดการติดตั้งจริง](../features/support-center-implementation.md) เนื้อหาด้านล่างเก็บไว้เป็นต้นฉบับการออกแบบ

ส่วนเพิ่มเติมตามคำขอ: [คะแนนขอบคุณผู้แจ้ง](support-rating-design.md) — ผู้ดูแลมอบคะแนนการมีส่วนร่วมและส่งคำขอบคุณหลังตรวจสอบข้อมูล พร้อมประวัติและยอดสะสมส่วนตัว

## เป้าหมายและขอบเขต

ให้พนักงานแจ้งปัญหา Application และปัญหาการทำงานอื่น ติดตามเจ้าของเรื่องและความคืบหน้าได้ในที่เดียว ใช้หน้าตา navy/blue ของ IoT Team Center และรองรับ TH/EN/JP ตามภาษาของระบบ ข้อความที่ผู้ใช้เขียนเก็บตามต้นฉบับ

รุ่นแรกครอบคลุมแจ้งเรื่อง แนบหลักฐาน รับเรื่อง มอบหมาย สนทนา เปลี่ยนสถานะ แจ้งเตือน และยืนยันปิดเรื่อง เป็นช่องทางสำหรับงานสนับสนุนทั่วไป; เรื่องบุคคลที่ต้องจำกัดการเข้าถึงเป็นพิเศษต้องมีช่องทาง/สิทธิ์ที่กำหนดไว้ก่อนนำมาใช้

## จุดเข้าใช้งานและหน้าจอ

1. ปุ่ม **แจ้งปัญหา** บน topbar ทุกหน้าหลังเข้าสู่ระบบ เปิดฟอร์มแบบ drawer บน desktop และเต็มหน้าบนมือถือ รักษาข้อมูลที่กำลังกรอกในหน้าต้นทางไว้
2. เมนู **ศูนย์แจ้งปัญหา / Support Center / サポートセンター** อยู่ช่วงท้าย sidebar ก่อนส่วนดูแลระบบ ทุกบัญชีที่ใช้งานได้เข้าถึงรายการของตนเอง
3. หน้า **รายการของฉัน**: เลขเรื่อง หัวข้อ หมวด สถานะ ผู้รับผิดชอบ และอัปเดตล่าสุด; ค้นหาและกรองสถานะ; เริ่มต้น 50 รายการต่อหน้า พร้อม pagination และจำนวนทั้งหมดตามแนวทางเดิมของโครงการ
4. หน้า **รายละเอียดเรื่อง**: หัวข้อและสถานะด้านบน รายละเอียด/หลักฐาน/ประวัติสนทนาด้านหลัก ผู้แจ้ง ผู้รับผิดชอบ ผลกระทบ วันเวลา และรายการที่เกี่ยวข้องด้านข้าง; มือถือเรียงแนวตั้ง
5. หน้า **คิวผู้ดูแล** แสดงเฉพาะผู้มีสิทธิ์: ใหม่/ยังไม่มีผู้รับผิดชอบ, งานของฉัน, กำลังดำเนินการ, รอข้อมูล และแก้ไขแล้ว กรองหมวด/ผู้รับผิดชอบ/ลำดับความสำคัญได้

แบบจำลองประกอบอยู่ที่ `output/support-center-design.html` ใช้ข้อมูลตัวอย่างในหน่วยความจำเพื่อสำรวจรายการ ฟอร์ม และคิวผู้ดูแล การส่งในแบบจำลองไม่ส่งเข้าแอปจริง

## หมวดและฟอร์มแจ้งปัญหา

| ช่อง | กติกาที่เสนอ |
| --- | --- |
| ประเภทเรื่อง | บังคับ: Application / อุปกรณ์และเครือข่าย / ข้อมูลและเอกสาร / การทำงานและประสานงาน / อื่น ๆ |
| หัวข้อ | บังคับ 5–160 ตัวอักษร; ตัวอย่าง “บันทึก Estimate แล้วขึ้นข้อผิดพลาด” |
| รายละเอียด | บังคับ 10–5,000 ตัวอักษร; ช่วยบอกสิ่งที่เกิดขึ้นและผลกระทบ |
| ผลกระทบ | บังคับ: ยังทำงานต่อได้ / งานบางส่วนติดขัด / ทำงานต่อไม่ได้; แยกจาก priority ที่ทีมดูแลคัดกรอง |
| หน้าที่พบปัญหา | Application: เติมชื่อโมดูล/record reference จากจุดที่กด ผู้แจ้งแก้ไขหรือนำออกได้; แจ้งจากศูนย์โดยตรงเลือกเองได้ |
| ขั้นตอนก่อนพบปัญหา / สิ่งที่คาดหวัง | ช่องเพิ่มเติมสำหรับ Application ไม่บังคับเพื่อให้ส่งเรื่องได้เร็ว |
| โครงการ / สถานที่ / อุปกรณ์ | ไม่บังคับ ปรับตามประเภทเรื่อง เลือก record ได้เฉพาะที่ผู้ใช้มีสิทธิ์ |
| เวลาที่พบ | ไม่บังคับ แยกจาก createdAt ของระบบ |
| ไฟล์แนบ | ไม่บังคับ เสนอเริ่มต้น PNG/JPEG/PDF ไม่เกิน 5 ไฟล์ ไฟล์ละ 10 MB; แสดงความคืบหน้าและลองแนบซ้ำได้ |
| ผู้แจ้งและเวลาส่ง | มาจากบัญชีและเวลาของ server ไม่ต้องกรอก |

ฟอร์มแสดงข้อมูลบริบทที่จะส่งอย่างชัดเจน: module, record ID, app version และ error correlation ID หากมี ห้ามเก็บ access token, cookies, รหัสผ่าน, raw query string หรือ form payload อัตโนมัติ ภาพหน้าจอเป็นการแนบโดยผู้แจ้ง ไม่จับภาพเอง

ปุ่มส่ง disabled ขณะรอผล ตรวจสอบช่องที่จำเป็น และรักษาข้อความเมื่อส่งล้มเหลว หากปิดฟอร์มที่มีข้อมูลให้เตือนก่อนทิ้ง เก็บ draft ในหน่วยความจำเฉพาะ session ของหน้าเป็นค่าเริ่มต้น ไม่เก็บข้อมูลแจ้งปัญหาใน localStorage

หลังส่งสำเร็จแสดงเลข **SUP-2026-00001** และปุ่มดูเรื่อง สร้างเลขบน server พร้อม unique constraint หากแนบไฟล์บางรายการไม่สำเร็จต้องบอกว่าเรื่องถูกสร้างแล้วและระบุไฟล์ที่ต้องลองใหม่ ไม่ให้ผู้ใช้สร้างเรื่องซ้ำ

## สถานะและการดำเนินการ

เส้นทางหลัก: **ใหม่ → รับเรื่องแล้ว → กำลังดำเนินการ → แก้ไขแล้ว → ปิดเรื่อง**

| สถานะ | ผู้ดำเนินการ / เงื่อนไข |
| --- | --- |
| ใหม่ (New) | ระบบกำหนดเมื่อส่งเรื่อง |
| รับเรื่องแล้ว (Acknowledged) | ผู้ดูแลรับเรื่องและกำหนดเจ้าของเรื่อง |
| กำลังดำเนินการ (InProgress) | ผู้รับผิดชอบเริ่มแก้ไข |
| รอข้อมูล (WaitingForReporter) | ผู้รับผิดชอบต้องระบุคำถาม; ผู้แจ้งตอบแล้วกลับ InProgress และแจ้งผู้รับผิดชอบ |
| แก้ไขแล้ว (Resolved) | ผู้รับผิดชอบต้องบันทึกวิธีแก้ไข; ผู้แจ้งเห็น “ยืนยันปิดเรื่อง” และ “ยังพบปัญหา” |
| ปิดเรื่อง (Closed) | ผู้แจ้งยืนยันหลัง Resolved; Support Admin ปิดแทนได้พร้อมเหตุผล |
| ยกเลิก (Cancelled) | ผู้แจ้งถอนเรื่องก่อน Closed หรือผู้ดูแลยกเลิกพร้อมเหตุผล เช่น แจ้งซ้ำ; เก็บประวัติ ไม่ลบ |

“ยังพบปัญหา” ต้องระบุรายละเอียด กลับ InProgress โดยเก็บ owner และประวัติเดิม สำหรับ Closed ผู้แจ้งขอเปิดเรื่องเดิมอีกครั้งได้พร้อมเหตุผล ไม่มีการปิดอัตโนมัติในรุ่นแรก ส่วน Cancelled ให้ส่งเรื่องใหม่และอ้างอิงเรื่องเดิม หากแจ้งซ้ำให้ผู้ดูแลเชื่อมเรื่องหลักโดยไม่เปิดเผยรายละเอียดเรื่องที่ผู้แจ้งไม่มีสิทธิ์ดู

Priority เป็น Low / Normal / High / Urgent และทีมดูแลเป็นผู้กำหนด ค่าเริ่มต้น Normal; งานที่ผู้แจ้งเลือก “ทำงานต่อไม่ได้” แสดงสัญลักษณ์ให้คัดกรองก่อน ยังไม่ผูก SLA เป็นเวลารับประกันจนกว่าจะมีผู้รับผิดชอบและเวลาทำการที่ตกลงกัน

## สิทธิ์และการสนทนา

| บทบาท | ขอบเขต |
| --- | --- |
| ผู้แจ้ง | สร้าง/อ่าน/ตอบ/แนบไฟล์ในเรื่องของตน ถอนเรื่อง ยืนยันปิด และขอเปิดใหม่ |
| Support Agent | อ่านคิวหมวดที่ได้รับสิทธิ์ รับเรื่องเอง ตอบสาธารณะ เปลี่ยนสถานะของงานที่รับผิดชอบ และเขียนบันทึกภายใน |
| Support Admin | จัดการเรื่องทั้งหมด มอบหมาย/ย้ายหมวด/priority จัดการสมาชิก support และปิดแทนพร้อมเหตุผล |

สิทธิ์เสนอ: `support.create`, `support.read.own`, `support.read.queue`, `support.assign`, `support.manage` ใช้สิทธิ์และขอบเขตหมวดร่วมกัน ไม่ให้ Leader หรือผู้ดูแล master data เห็นเรื่องทั้งหมดโดยอัตโนมัติ

ทุก API ตรวจ object-level access รวม comments, attachments และ notifications. การเชื่อม Project/Estimate ไม่มอบสิทธิ์ดูเอกสารต้นทางเพิ่ม เจ้าของโครงการไม่เห็น ticket ของผู้อื่นโดยอัตโนมัติ

บันทึกภายในแยกชัดเจนจาก “ตอบผู้แจ้ง” และไม่ส่งใน payload/ไฟล์แนบ/notification ของผู้แจ้ง ประวัติรวมการมอบหมาย เปลี่ยนสถานะ priority และเหตุผล; ไม่มี hard delete ผ่านหน้าจอรุ่นแรก ผู้ดูแลหมวดที่ย้ายออกเสียสิทธิ์ทันทีตามขอบเขตใหม่

## แจ้งเตือนและกรณีผิดปกติ

- ใช้กระดิ่งเดิม: เรื่องใหม่ถึงผู้คัดกรองหมวดนั้น; มอบหมายถึงผู้รับผิดชอบ; คำถาม/คำตอบ/แก้ไขแล้วถึงคู่สนทนาที่เกี่ยวข้อง; เปิดใหม่ถึงผู้รับผิดชอบ ไม่แจ้งเตือนการกระทำกลับหาตนเอง
- Notification ต้องเปิด ticket นั้นโดยตรงและตรวจสิทธิ์อีกครั้ง เมื่อไฟล์หรือเรื่องหมดสิทธิ์ให้แสดง “ไม่สามารถเข้าถึงเรื่องนี้ได้” ไม่รั่วหัวข้อหรือข้อความ
- ระบุผู้คัดกรองกลางเมื่อหมวดไม่มีผู้รับผิดชอบ เพื่อไม่ให้เรื่องตกหล่น การแจ้งเตือนผิดพลาดต้องไม่ทำให้ ticket ที่บันทึกสำเร็จหายไป
- หน้าไม่มีรายการแสดง “ยังไม่มีเรื่องที่แจ้ง” พร้อมปุ่มแจ้งใหม่ แยก loading, empty, error และ retry ชัดเจน
- API ใช้งานไม่ได้: คงข้อความในฟอร์ม แสดงส่งไม่สำเร็จ และช่องทางติดต่อสำรองที่องค์กรตั้งค่าไว้ ไม่แสดงเลขเรื่องปลอม หน้าล็อกอินแสดงช่องทางสำรองเดียวกันเมื่อผู้ใช้เข้าแอปไม่ได้
- รองรับ keyboard, focus return เมื่อปิด drawer, label ทุก field และสถานะมีข้อความร่วมกับสี

## แนวทางต่อกับโค้ดเดิม (ยังเป็นข้อเสนอ)

หลักฐานจาก source: `ProductionApp.tsx` มี View/NAV, bootstrap permissions, notification menu และ `openNotification`; `api-client.ts` มี notification API และระบบ request เดิม; `app/globals.css` มี token navy/blue และสีสถานะอยู่แล้ว. `issues` ใน shell หมายถึง Material Issues จึงใช้ชื่อ `support` / `SupportTicket` แยกโดยเด็ดขาด

เพิ่ม screen `production/SupportScreens.tsx` และ style ที่มี scope เฉพาะ; ต่อ production View/NAV/topbar พร้อม guard ข้อมูลที่ยังไม่บันทึก; ต่อ `openNotification` สำหรับ `entityType: SupportTicket` โดยเก็บ selected ticket ID/deep-link ให้ refresh แล้วยังเปิดเรื่องเดิมได้ ตรวจ router ที่ใช้จริงก่อนกำหนด URL สุดท้าย

Repository มีทั้ง Node และ .NET backend; ต้องยืนยัน target release ก่อนลงมือ implement ไม่ถือ README เก่าเป็นข้อสรุป runtime. เลือก migration number ถัดไปตอนเริ่มพัฒนาเพื่อไม่ชนงานร่วมกัน

### โครงสร้างข้อมูลที่เสนอ

- `SupportTickets`: id, ticketNo, categoryId, reporterId, assigneeId, subject, description, impact, priority, status, contextJson (allowlist), createdAt, updatedAt, resolvedAt, closedAt, version
- `SupportComments`: ticketId, authorId, body, visibility (`public` / `internal`), createdAt
- `SupportAttachments`: ticketId, commentId?, uploaderId, visibility, storageKey, originalName, mimeType, size, sha256, scanStatus, createdAt
- `SupportEvents`: ticketId, actorId, eventType, previous/new values, reason, createdAt (append-only)
- `SupportCategories` และสมาชิกผู้รับผิดชอบ: ใช้ permission model เดิมร่วมกับขอบเขตหมวด

SQL เก็บ metadata; ไฟล์ใช้ storage service ที่มีอยู่ผ่าน API เพิ่มขอบเขต support โดยเฉพาะ ไม่เปิด public URL และต้องตรวจ MIME/size/scan state ฝั่ง server. จัดการ orphan uploads และกำหนด retention ในงาน implementation

### API ที่เสนอ

`GET/POST /api/v1/support/tickets`, `GET /api/v1/support/tickets/:id`, `POST .../:id/comments`, `POST .../:id/attachments`, `GET .../:id/attachments/:attachmentId`, `POST .../:id/assign`, `POST .../:id/transition`, `GET /api/v1/support/categories`

List ใช้ scope mine/queue, pagination และ sort ฝั่ง server; scope queue ต้องมีสิทธิ์. Create ใช้ idempotency key ป้องกันส่งซ้ำ; assign/transition ใช้ version ป้องกันทับการแก้ไขกันและคืน 409 เมื่อข้อมูลเปลี่ยน. เปลี่ยน ticket และเขียน event ใน transaction เดียวกัน; notification ใช้กลไก retry/outbox ที่เหมาะกับ backend จริง

## เกณฑ์รับงานสำหรับ implementation

1. ทุกบัญชี active แจ้ง Application/อื่น ๆ ได้ รับเลขเรื่องจริง และพบในรายการของตนหลัง reload
2. แจ้งจาก Estimate แล้วเห็น module/record ที่จะส่ง และข้อมูล Estimate ที่ยังไม่บันทึกไม่หาย
3. ผู้ใช้ A เดา ticket/comment/attachment ID ของ B แล้วเข้าถึงไม่ได้ รวม list และ notifications
4. ผู้ดูแลรับเรื่อง มอบหมาย รอข้อมูล แก้ไข; ผู้แจ้งตอบ ยืนยันปิด หรือเปิดใหม่ได้ตาม transition เท่านั้น พร้อม event log
5. Internal note และไฟล์ของ note ไม่ปรากฏในข้อมูลหรือการแจ้งเตือนฝั่งผู้แจ้ง
6. คลิก notification เปิดเรื่องตรงรายการพร้อมตรวจสิทธิ์; ข้อผิดพลาดแสดงอย่างชัดเจน
7. Double-submit, retry หลัง timeout, concurrent assignment และไฟล์แนบบางไฟล์ล้มเหลวไม่สร้างข้อมูลซ้ำหรือแจ้งสำเร็จผิด
8. มือถือ/desktop, TH/EN/JP, keyboard และ empty/error states ใช้ได้; รายการเกิน 50 เข้าถึงหน้าถัดไปได้

## ลำดับพัฒนาที่เสนอ

รุ่นแรก: ฟอร์ม + รายการของฉัน + รายละเอียด/ไฟล์/สนทนา + คิวผู้ดูแล + สิทธิ์/ประวัติ + กระดิ่ง + lifecycle ครบวงจร

ระยะต่อไป: Email/Teams หลังตั้งค่าผู้รับและช่องทาง, SLA/เวลาทำการ/การยกระดับ, FAQ จากเรื่องที่แก้แล้ว, dashboard แนวโน้มปัญหา และระบบจัดการเรื่องละเอียดอ่อนเฉพาะทาง

ค่าตั้งต้นที่เสนอให้ใช้ตอนพัฒนา: แจ้งเตือนในแอปก่อน, 5 หมวดข้างต้น, ไฟล์สูงสุด 5 × 10 MB, ไม่มี auto-close. ผู้ดูแลศูนย์และช่องทางสำรองเป็นค่าที่องค์กรต้องกำหนดก่อนเปิดใช้จริง
