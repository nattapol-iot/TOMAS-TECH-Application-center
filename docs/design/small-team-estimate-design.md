# Inquiry และ Estimate สำหรับทีมเล็กที่รับงานด่วน

สถานะ: Draft · 10 กันยายน 2026 · ข้อกำหนดการออกแบบภายใต้ [DESIGN.md](../../DESIGN.md)

## โจทย์และหลักฐาน

ผู้ใช้ระบุปัญหา: Inquiry ด่วนจำนวนมาก เจ้าของงานไม่ชัด ไฟล์กระจัดกระจาย ไม่อัปเดต Revision แม่แบบเปลี่ยนบ่อย ไม่มี Overhead และค้นราคาอ้างอิงยาก เป้าหมายคือให้ทีมทำงานต่อกันได้โดยไม่ต้องถามว่าใครทำ ไฟล์ไหนล่าสุด และราคานี้มาจากไหน

ของเดิมที่ต้องใช้ต่อ:
- `app/system/production/InquiryScreens.tsx`: เจ้าของ Inquiry/Estimate และทางลัดไป Estimate
- `app/system/production/EstimateScreens.tsx`: Assignment, แท็บ Revision/Compare, Template, Price Library, Excel import/export และ Contingency
- `docs/estimate-excel-import.md`: เก็บ provenance ของข้อมูลนำเข้า แต่ไม่เก็บ bytes ของไฟล์ Excel ต้นฉบับ และไม่รวม profit/overhead ในต้นทุนตรง
- `docs/inquiry-estimate-ux-release.md`: ปรับ Local ให้มี next-step guide และแจ้ง missing rate ก่อนบันทึกแล้ว ยังไม่ได้แก้การจัดเก็บไฟล์หรือนโยบายต้นทุน
- `docs/estimate-cost-workspace-design.md`: คงเก้าแท็บ ตาราง และวิธีแก้ไขเดิม ไม่ออกแบบหน้าทดแทนทั้งหมด

หลักฐานเป็นคำอธิบายผู้ใช้ โค้ด เอกสาร และการทดลองงาน INQ-2609-0015/EST-2609-0015 ด้วย Admin ยังไม่มีการวัดเวลาทำงานจริงของ Engineer, ทดสอบมือถือครบ หรือยืนยันการสร้างโฟลเดอร์บน NAS ในรอบนี้

## ข้อตกลงหลักที่เสนอ

**หนึ่ง Inquiry มีผู้รับผิดชอบหลักที่ชัด หนึ่ง Estimate มีฉบับทำงานปัจจุบันที่หาเจอ และแต่ละราคาย้อนกลับไปยังหลักฐานได้**

งานด่วนไม่ต้องผ่านขั้นอนุมัติเพิ่มเพียงเพื่อเริ่มร่าง แต่ข้อมูลที่ยังไม่ทราบต้องเห็นชัด และห้ามอ้างว่าพร้อมส่งแล้ว

## ขั้นตอนทำงาน

1. รับเรื่อง: ระบุลูกค้า งานที่ต้องการ และวันเวลาที่ลูกค้ารอคำตอบ แนบไฟล์ได้ทันที ข้อมูลที่ยังไม่ครบอยู่ในคิวรอคัดแยกและมีผู้ดูแลคิว
2. จัดงาน: หัวหน้าทีมเลือกเจ้าของ Estimate หลักหนึ่งคน ผู้ช่วยเป็นรายหมวด และกำหนดเวลาส่งต้นทุนภายใน แยกจากเวลาตอบลูกค้า
3. เริ่มประมาณการ: ใช้แม่แบบที่เผยแพร่หรือคัดลอกจากงานเก่า แสดงต้นทางและเวอร์ชันก่อนใช้ ไม่ต้องสร้างโฟลเดอร์เอง
4. เติมต้นทุน: วัสดุ ค่าแรง ค่าใช้จ่ายตรงอื่น และ Overhead ที่แสดงฐานคำนวณชัด เลือกราคาอ้างอิงพร้อมหลักฐาน
5. ส่งตรวจ: ตรวจเฉพาะปัญหาที่ขวางการส่งก่อน คำเตือนรวมเป็นกลุ่ม ผู้รับผิดชอบกดส่งฉบับปัจจุบันเพื่อสร้าง snapshot ที่แก้ย้อนหลังไม่ได้
6. แก้ไข: ถ้าส่งตรวจหรือเผยแพร่ไปแล้ว ระบบสร้าง Revision ถัดไปให้อัตโนมัติเมื่อเริ่มแก้ พร้อมเหตุผลสั้น ๆ และเปรียบเทียบสิ่งที่เปลี่ยน การบันทึกร่างแต่ละครั้งไม่เพิ่มเลข Revision
7. ส่งต่องาน: ใช้ฉบับอนุมัติที่ระบุชัดส่งต่อกระบวนการขาย/โปรเจกต์ พร้อมไฟล์และหลักฐานชุดเดียวกัน ไม่เปลี่ยน Draft เป็นฉบับอนุมัติเอง

## 1. เจ้าของงานและคิวงาน

- หน้ารายการเริ่มจาก «งานของฉัน» สำหรับ Engineer; หัวหน้ามี «งานทีม» และ «ยังไม่มอบหมาย»
- แถวงานแสดงชื่องาน เจ้าของหลัก กำหนดส่ง ขั้นถัดไป และสิ่งที่รอ เช่น «รอราคา Sensor จากผู้ขาย»
- งานที่ยังไม่มอบหมายต้องไม่ถูกซ่อน ต้องแสดงผู้ดูแลคิวที่รับผิดชอบคัดแยก
- เปลี่ยนเจ้าของได้ตามสิทธิ์และบันทึกประวัติ เจ้าของหลักยังรับผิดชอบรวมงานแม้มีผู้ช่วยหลายคน
- แสดงจำนวนงานค้างของคนที่จะมอบหมายเพื่อช่วยตัดสินใจ ไม่มอบหมายอัตโนมัติจากจำนวนงานอย่างเดียว
- ปุ่มสถานะสั้น: «กำลังทำ», «รอข้อมูล», «รอราคา», «พร้อมตรวจ»; สถานะรอต้องระบุสิ่งที่รอ ไม่ให้ผู้ใช้กรอกเปอร์เซ็นต์แทนข้อเท็จจริง

## 2. ไฟล์และเอกสารชุดเดียว

- ผูกไฟล์กับ Inquiry/Estimate ID และ Revision ไม่พึ่งชื่อไฟล์หรือ path เป็นตัวระบุเอกสาร
- พื้นที่เอกสารแบ่งตามงาน: ข้อมูลลูกค้า / เอกสารราคาอ้างอิง / ไฟล์ทำงาน / ฉบับส่งตรวจและอนุมัติ
- Import Excel ต้องเก็บต้นฉบับพร้อม checksum, ผู้เพิ่ม, เวลา, import receipt และ Revision ที่นำเข้า; หากเก็บไฟล์ไม่ได้ต้องแจ้งและไม่อ้างว่านำเข้าครบกระบวนการ
- Export ตั้งชื่อจากข้อมูลระบบ เช่น `EST-2609-0015_R00_DRAFT.xlsx`; ไฟล์ที่เผยแพร่แสดงเลข Revision สถานะ และวันที่สร้างภายในเอกสารด้วย
- UI แยก «ร่างล่าสุด» กับ «ฉบับอนุมัติล่าสุด» ให้เห็นพร้อมกัน ไม่เรียกทั้งสองอย่างว่า «ไฟล์ล่าสุด»
- เมื่อแก้ Excel ภายนอก ให้นำกลับเข้าฉบับร่างผ่านการตรวจ diff ก่อนบันทึก เก็บต้นฉบับเดิม ไม่รับประกัน sync Excel อัตโนมัติ
- NAS เป็นปลายทางจัดเก็บ ระบบต้องแสดงกำลังส่ง/สำเร็จ/ส่งไม่สำเร็จ และ retry ได้ การมีแถว metadata ไม่ใช่หลักฐานว่าไฟล์อยู่บน NAS แล้ว
- การย้ายไฟล์เก่าเริ่มจากรายการสำรวจและผูกกับงานที่ถูกต้อง ไม่ลบต้นฉบับอัตโนมัติ

## 3. Revision ที่ไม่ต้องจำตั้งชื่อเอง

- เริ่ม R00; autosave หรือกดบันทึกอัปเดตร่างเดิมพร้อมประวัติผู้แก้และเวลา
- การส่งตรวจสร้าง snapshot; การแก้ snapshot ต้องเปิด Revision ถัดไปโดยระบบออกเลขและกันเลขชน
- ให้เหตุผล เช่น เปลี่ยน Scope / ลูกค้าแก้ Requirement / ราคาใหม่ / แก้ข้อมูล และแสดง diff ของรายการ ยอด และไฟล์
- ฉบับที่ลูกค้าหรือผู้ตรวจได้รับแล้วไม่ถูกเขียนทับ การเลือกใช้งานฉบับอนุมัติไม่เปลี่ยนตามร่างล่าสุด
- ต้องออกแบบ migration ให้เข้ากับ workflow Submitted/Approved/Locked และการสร้าง Revision เดิมก่อนเขียนโค้ด ไม่เปิดสิทธิ์แก้ immutable record เพื่อทำ UX ให้สั้นลง

## 4. แม่แบบที่นิ่งแต่ปรับปรุงได้

- สมาชิกใช้แม่แบบ Published เป็นค่าเริ่มต้น ผู้ดูแลแม่แบบแก้ผ่าน Draft และเผยแพร่เวอร์ชันใหม่
- งานบันทึก template ID/version และ snapshot ตอนเริ่มใช้ การแก้แม่แบบไม่เปลี่ยนงานเก่า
- ใช้แม่แบบตามชนิดงานจริงของทีม เริ่มจากงานที่ใช้ซ้ำบ่อย ไม่สร้างชุดจำนวนมากก่อนมีหลักฐานการใช้
- แม่แบบกำหนดโครงรายการ หมวด งานวิศวกรรม สมมติฐานและ exclusions; ราคาในแม่แบบต้องระบุว่าเป็นเพียงค่าเริ่มต้นและแสดงอายุราคา
- หากไม่มีแม่แบบที่เผยแพร่ ให้เริ่มร่างเปล่าได้โดยระบุสถานะ ไม่คัดลอกแม่แบบทดลองมาใช้เงียบ ๆ

## 5. Overhead ที่ตรวจสอบได้

- เพิ่ม Overhead เป็นองค์ประกอบต้นทุนแยกจากค่าใช้จ่ายตรง, Contingency และกำไร
- ให้หัวหน้าที่มีสิทธิ์กำหนดนโยบายส่วนกลาง: วิธีคิด ฐานคำนวณ อัตรา วันที่มีผล และเหตุผลเปลี่ยนแปลง; ผู้กรอกใช้ค่าเริ่มต้นโดยไม่ต้องพิมพ์สูตร
- ผู้ใช้ยืนยันว่าไม่มีเกณฑ์และให้เสนอ: เริ่มเสนอการกระจาย Overhead ตามชั่วโมงวิศวกรรมภายในที่ใช้กับโครงการจริง โดยอัตรายังต้องคำนวณจากข้อมูลทีม ไม่ตั้งเปอร์เซ็นต์โดยไม่มีฐาน
- แสดงสูตรและจำนวนเงิน เช่น `ฐานที่เข้าเกณฑ์ × อัตรา`; ตัวเลขทั้งหมดคำนวณที่ server และเก็บ policy snapshot ต่อ Revision
- ถ้ายังไม่ตั้งค่า แสดง «ยังไม่ตั้ง Overhead» แทน 0; กรณีใช้ 0 ต้องเป็นนโยบายหรือข้อยกเว้นที่ระบุชัด
- ตรวจไม่ให้นับค่าใช้จ่ายเดียวกันซ้ำระหว่างค่าแรง ค่าใช้จ่ายตรง Overhead และยอดจาก Excel
- ก่อนเปิดใช้ต้องตกลงฐาน Contingency และผลต่อยอดรวม/export/project handover โดยรักษา historical totals ไม่คำนวณงานเก่าทับ

### เกณฑ์ Overhead เริ่มต้นที่เสนอ

ใช้สำหรับการประมาณต้นทุนบริหารภายใน ยังไม่ใช่นโยบายการลงบัญชีหรืออัตราที่อนุมัติแล้ว:

`อัตรา Overhead ต่อชั่วโมง = งบค่าใช้จ่ายส่วนกลางของทีมต่อเดือน ÷ ชั่วโมงงานตรงที่ทีมทำได้ตามปกติต่อเดือน`

`Overhead ของงาน = ชั่วโมงงานตรงภายในที่ประมาณไว้ × อัตรา Overhead ต่อชั่วโมง`

แนวคิด estimated overhead / estimated activity base อ้างอิง [OpenStax: Predetermined overhead](https://openstax.org/books/principles-managerial-accounting/pages/4-4-compute-a-predetermined-overhead-rate-and-apply-overhead-to-production) การเลือกชั่วโมงวิศวกรรมเป็นฐานเป็นข้อเสนอเฉพาะบริบททีมนี้ ต้องทวนกับสัดส่วนงานจริง

- งบส่วนกลาง: software license ที่ใช้ร่วม, IT/NAS, ค่าเช่าหรือค่าใช้สำนักงานส่วนที่ทีมรับผิดชอบ, งานธุรการและการประสานงานที่ไม่ได้คิดตรงให้งาน โดยแต่ละค่าใช้จ่ายอยู่ได้เพียงหนึ่งหมวด
- ค่าแรงทำโครงการ, เดินทางเฉพาะงาน, ผู้รับเหมาช่วง, license ที่ซื้อให้งานหนึ่งโดยเฉพาะ คิดเป็นต้นทุนตรง ไม่ใส่ซ้ำในส่วนกลาง
- ชั่วโมงฐานใช้กำลังทำงานปกติที่ทำงานตรงได้จริงหลังหักลา ประชุม ฝึกอบรม และงาน presales ไม่ใช้ชั่วโมงเข้างานทั้งหมด และไม่ลดตัวหารตามเดือนที่งานน้อยจนราคาแกว่ง
- เงินเดือนส่วนเวลาทำงานที่ไม่ใช่งานตรงจะอยู่ในค่าแรงกลางหรือ Overhead อย่างใดอย่างหนึ่งเท่านั้น ต้องตรวจวิธีคำนวณ Rate Master ก่อนใช้อัตรานี้
- ตัวอย่างสมมติ: ส่วนกลาง 60,000 บาท/เดือน และงานตรง 400 ชั่วโมง/เดือน → 150 บาท/ชั่วโมง งานใช้ 40 ชั่วโมง → Overhead 6,000 บาท ตัวเลขนี้เป็นตัวอย่างอธิบาย ไม่ใช่ค่าเริ่มต้นที่จะบันทึกลงระบบ
- งานขายอุปกรณ์ล้วน/จ้างภายนอกที่ใช้เวลาภายในต่ำ อาจต้องมีฐานจัดซื้อ/ประสานงานแยก ให้เก็บชั่วโมงประสานงานที่เกิดจริงก่อนเพิ่มสูตร ห้ามสรุปว่า overhead เป็นศูนย์เพียงเพราะไม่มีงานออกแบบ
- เริ่มนโยบายชั่วคราวจากงบประมาณที่หัวหน้าทบทวน เก็บ version/วันที่มีผล ตรวจยอดที่กระจายได้เทียบค่าใช้จ่ายจริงทุกเดือน และทบทวนอัตรารายไตรมาส ไม่แก้อัตราย้อนหลังในฉบับเผยแพร่
- แสดงต้นทุนตรง + Overhead + Contingency แยกกัน; กำไร/ราคาขายเป็นขั้นที่ต่างออกไป โดยฐาน Contingency ต้องกำหนดก่อน implementation

### ข้อตกลงการคำนวณที่นำไปใช้

- `ต้นทุนตรง = วัสดุ + ค่าแรงวิศวกรรม + Outsource + เดินทาง + ที่พัก + ต้นทุนตรงอื่น`
- `Contingency = ต้นทุนตรง × อัตรา Contingency เดิม` เพื่อไม่เปลี่ยนความหมายของใบ Estimate ที่มีอยู่ และไม่คิด Contingency ซ้ำบน Overhead
- `Overhead = ชั่วโมงงานตรงภายใน × อัตรา Overhead ต่อชั่วโมงของ Policy ที่ snapshot ไว้กับ Revision`
- `ยอดรวม = ต้นทุนตรง + Contingency + Overhead`; กำไรและราคาขายยังไม่รวมในยอดนี้
- Revision ที่ไม่มี Policy แสดงสถานะ `Missing` และจำนวน Overhead เป็นค่าว่าง ไม่แสดงเป็นศูนย์ ยอดรวมเดิมยังใช้งานและส่งตรวจได้พร้อมคำเตือน เพื่อไม่ทำให้งานเก่าหยุดทั้งหมด
- Policy ที่งบส่วนกลางเป็นศูนย์เป็น `Zero` อย่างชัดเจนและต้องมีเหตุผล ส่วนเลขศูนย์ที่เกิดจากการไม่ตั้งค่าหรือการปัดเศษไม่ถือเป็น Policy
- งานที่เริ่มตอนยังไม่มี Policy จะไม่รับ Policy ใหม่ตอนกดส่งโดยอัตโนมัติ เจ้าของต้องกดใช้ Policy อย่างชัดเจน หรือเปิด Revision ใหม่ จึงไม่มียอดเพิ่มโดยผู้ใช้ไม่เห็น
- Policy และ snapshot เป็นแบบ append-only; การสร้าง Revision ใหม่เลือก Policy ที่มีผลล่าสุด ณ วันนั้น งานที่อนุมัติแล้วและ submission snapshot ไม่ถูกคำนวณย้อนหลัง
- อ่าน Policy ใช้สิทธิ์ `master.read`; สร้าง Policy ใช้ `master.write` และจำกัดเพิ่มที่ Engineering Manager/Admin; ใช้ Policy กับ Estimate ใช้ `estimate.write` และจำกัดที่เจ้าของงาน/Engineering Manager/Admin พร้อมตรวจ `rowVersion`

## 6. หาและใช้ราคาอ้างอิง

- ใช้ Price Library เดิม เพิ่มการค้นด้วย Part No., ยี่ห้อ รุ่น รายละเอียด ผู้ขาย และงานเก่า
- ผลลัพธ์แสดงราคา หน่วย สกุลเงิน จำนวนที่ใช้อ้างอิง วันที่ ผู้ขาย แหล่งเอกสาร และอายุ/วันหมดอายุ พร้อมเปิดหลักฐานจากแถวนั้น
- ราคางานเก่าเป็นข้อมูลอ้างอิง ไม่ประกาศว่าเป็นราคาปัจจุบัน; ห้ามเลือกถูกที่สุดอัตโนมัติเมื่อหน่วย จำนวน หรือเงื่อนไขต่างกัน
- «ใช้ราคานี้» เติมข้อมูลและ provenance ลงร่างหนึ่งครั้ง โดยไม่เปลี่ยนยอดงานอื่นเมื่อคลังราคาอัปเดต
- ไม่มีราคา: ให้เจ้าของตั้งสถานะรอผู้ขาย หรือใช้ราคาประมาณพร้อมเหตุผลตามนโยบายที่ตกลง; ห้ามสร้างราคาเทียมเพื่อผ่าน Validation

## ลำดับส่งมอบ

1. เจ้าของงาน/คิวงาน + ศูนย์ไฟล์ผูก Revision: ลดการตามคนและหาไฟล์ผิดฉบับก่อน
2. แม่แบบเผยแพร่แบบมีเวอร์ชัน + ใช้ราคาอ้างอิงพร้อมหลักฐาน: ลดการเริ่มใหม่และคัดลอกผิด
3. นโยบาย Overhead และผลต่อยอดรวม: เริ่มหลังยืนยันสูตร พร้อม regression ของ import/export/revision/project handover

## เกณฑ์รับงานและทดสอบ

- Engineer เปิดงานที่รับผิดชอบและชี้ไฟล์ทำงาน/ฉบับอนุมัติถูกต้องได้ใน 10 วินาที (เป้าหมาย ไม่ใช่ผลที่วัดแล้ว)
- ไม่มีงานหลุดจากคิวเพราะยังไม่มอบหมาย; เปลี่ยนเจ้าของต้องมี audit
- ส่งตรวจแล้วแก้ต่อสองคนพร้อมกันไม่เขียนทับ snapshot หรือสร้าง Revision เลขซ้ำ
- เปลี่ยนแม่แบบหรือ rate policy ไม่เปลี่ยนยอดและไฟล์ของ Revision ที่เผยแพร่แล้ว
- Import ซ้ำไม่เพิ่มต้นทุนซ้ำ และการอัปโหลดล้มเหลวต้องไม่แสดงไฟล์ว่าพร้อมใช้
- ทดสอบ Overhead ที่ยังไม่กำหนด/0/อัตราต่อชั่วโมง/เปลี่ยนนโยบาย รวมการปัดเศษและการนับซ้ำตามสูตรที่ตกลง
- ทดสอบราคาเก่า หน่วยต่าง สกุลเงินต่าง แหล่งราคาเข้าไม่ได้ และ role ที่ไม่มีสิทธิ์ดูราคา
- เปรียบเทียบงานตัวอย่างเดียวกันกับวิธีเดิม วัดเวลาค้นไฟล์/ราคา จำนวนครั้งถามเจ้าของ และข้อผิดพลาด Revision; เป้าลดเวลารวมอย่างน้อย 20% โดยไม่ลดความถูกต้อง
- ใช้ Engineer และหัวหน้าจริง ทดสอบคีย์บอร์ด ภาษาไทย/อังกฤษ/ญี่ปุ่น หน้าจอเล็ก และเครือข่ายช้า
