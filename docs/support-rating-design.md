# คะแนนขอบคุณผู้แจ้ง — Contribution Points

ข้อเสนอออกแบบ 6 กันยายน 2026 ต่อจาก [ศูนย์แจ้งปัญหา](support-center-design.md) ผู้ใช้ยืนยันว่าเป้าหมายคือ “ให้คะแนนและขอบคุณที่แจ้งเข้ามา” เพื่อยอมรับการมีส่วนร่วมของผู้แจ้ง ไม่ใช่แบบประเมินความพึงพอใจของทีม support

สถานะ: เพิ่มระบบคะแนนขอบคุณในแอปจริงแล้ว ดู [รายละเอียดการติดตั้งจริง](support-center-implementation.md) เนื้อหาด้านล่างเก็บไว้เป็นต้นฉบับการออกแบบ ยังไม่มีการมอบคะแนนจริงเพื่อทดสอบ

## ประสบการณ์ที่เสนอ

1. ผู้ใช้ส่งเรื่องสำเร็จ → แสดง “ขอบคุณที่ช่วยแจ้งปัญหาให้ทีมครับ” พร้อมเลขเรื่องและ “คะแนนขอบคุณ: รอตรวจสอบ” ข้อความขอบคุณเกิดหลัง server บันทึกเรื่องสำเร็จ ไม่รอคะแนน
2. ผู้ดูแลตรวจสอบ → ส่วน “ขอบคุณผู้แจ้ง” ในหน้ารายละเอียดเรื่อง มีเกณฑ์คะแนนที่เลือกได้และช่องข้อความขอบคุณ ไม่จำเป็นต้องรอแก้ปัญหาเสร็จ
3. ผู้ดูแลเห็นสรุปคะแนน ผู้รับ และข้อความที่จะส่ง → กด **มอบคะแนนและขอบคุณ** บันทึกคะแนนกับ event และคิว notification ใน transaction เดียวกัน
4. ผู้แจ้งได้รับกระดิ่ง “คุณได้รับ 8 คะแนนขอบคุณจากเรื่อง SUP-…” เปิดไปดูรายละเอียดได้ พร้อมข้อความเฉพาะเรื่อง เช่น “ขอบคุณสำหรับขั้นตอนและภาพประกอบ ช่วยให้ทีมพบจุดที่บันทึกค่าแรงผิดพลาดได้เร็วขึ้น”
5. ใน “รายการของฉัน” แต่ละเรื่องแสดง รอตรวจสอบ / ได้รับ N คะแนน / ขอบคุณแล้ว และแสดงคะแนนสะสมจากเรื่องที่ตัวเองแจ้ง พร้อมประวัติที่ตรวจสอบได้

ใช้ชื่อ **คะแนนขอบคุณ** และ **การมีส่วนร่วม** ใน UI. ไม่ใช้ดาวประเมินบุคคล ไม่ลดคะแนนเพราะแจ้งปัญหา และไม่กำหนดให้แจ้งเป็นจำนวนมากจึงถือว่ามีผลงาน

## เกณฑ์เริ่มต้นที่เสนอ: สูงสุด 10 คะแนนต่อเรื่อง

| เกณฑ์ | คะแนน | หลักฐานที่ใช้พิจารณา |
| --- | ---: | --- |
| ข้อมูลมีประโยชน์ต่อการตรวจสอบหรือปรับปรุง | +5 | ระบุประเด็นที่ทีมตรวจสอบต่อได้ รวมข้อสงสัย/ปัญหาการใช้งานที่นำไปปรับคำแนะนำได้ ไม่ต้องยืนยันว่าเป็น bug |
| มีรายละเอียดช่วยตรวจสอบได้เร็ว | +3 | ขั้นตอน เวลา บริบท หรือหลักฐานที่เพียงพอ ไม่บังคับภาพหน้าจอหรือความรู้ทางเทคนิค |
| มีข้อเสนอหรือข้อมูลเพิ่มเติมที่นำไปใช้ได้ | +2 | แนวทางป้องกัน วิธีหลีกเลี่ยง หรือข้อมูลใหม่ที่ผู้ดูแลยืนยันว่านำไปใช้ต่อได้ |

คะแนนรวม = ผลรวมเกณฑ์ที่ผ่าน โดย +3/+2 ต้องผ่านเกณฑ์ +5 ก่อน ไม่มีช่องพิมพ์คะแนนอิสระในรุ่นแรก. ค่าที่เป็นไปได้คือ 5, 7, 8, 10; ถ้าไม่ผ่านเกณฑ์พื้นฐานส่ง **ขอบคุณโดยไม่เพิ่มคะแนน** ได้ โดยไม่แสดงเลข 0 หรือคำว่า “ไม่ผ่าน” ต่อผู้แจ้ง

ตัวอย่าง: แจ้งว่าบันทึก Estimate ไม่ได้พร้อมขั้นตอนที่ทำซ้ำได้ → 8 คะแนน; มีข้อมูลช่วยป้องกันปัญหาที่นำไปใช้ต่อได้ → 10 คะแนน. ความร้ายแรงหรือจำนวนผู้ได้รับผลกระทบไม่เพิ่มคะแนนโดยอัตโนมัติ เพราะผู้แจ้งปัญหาเล็กก็ช่วยพัฒนางานได้

หมวดอื่นใช้เกณฑ์เดียวกัน เช่น ระบุอุปกรณ์/สถานที่และอาการให้ตรวจต่อได้ หรือชี้จุดที่เอกสารไม่ชัดเจน ไม่ต้องเป็นปัญหา Application

## เรื่องซ้ำ การตรวจสอบ และการมอบคะแนน

- มอบคะแนนได้ตั้งแต่รับเรื่องและตรวจสอบข้อมูลแล้ว แม้กำลังดำเนินการหรือรอข้อมูล ไม่ผูกคะแนนกับเวลาที่ทีมแก้ปัญหาเสร็จ
- เรื่องใหม่ที่ยังไม่ตรวจสอบแสดง “รอตรวจสอบ”; การขอบคุณทันทีหลังส่งไม่ใช่การรับรองคะแนน
- หนึ่ง ticket มี recognition ที่มีผลปัจจุบันหนึ่งรายการ ให้ผู้แจ้งเจ้าของเรื่องจาก server เท่านั้น ไม่เลือกผู้รับเอง
- เรื่องซ้ำที่ไม่มีข้อมูลเพิ่ม: เชื่อมเรื่องหลักและขอบคุณโดยไม่เพิ่มคะแนน; เรื่องซ้ำที่มีข้อมูลใหม่ช่วยวิเคราะห์ได้ยังพิจารณาให้คะแนนตามข้อมูลใหม่ โดยบันทึกเหตุผล ผู้แจ้งไม่เห็นข้อมูลเรื่องหลักหากไม่มีสิทธิ์
- เมื่อยังมีข้อมูลไม่พอ ให้ขอข้อมูลและคงสถานะรอตรวจสอบ ไม่ตัดสินเป็น 0 คะแนน
- ผู้ดูแลต้องระบุข้อความขอบคุณเฉพาะเรื่องก่อนส่ง (10–1,000 ตัวอักษร) สามารถแก้ข้อความร่างที่ระบบแนะนำได้
- คะแนนไม่มีผลกับ priority, สิทธิ์ใช้งาน, SLA หรือคิวการแก้ปัญหา เรื่องไม่มีคะแนนยังดำเนินการตาม workflow ปกติ
- รุ่นแรกไม่มีแลกรางวัล badge หรือ leaderboard สาธารณะ และไม่ส่งเข้าคะแนน KPI อัตโนมัติ สามารถพิจารณาประวัติเป็นหลักฐานการมีส่วนร่วมในอนาคตเมื่อองค์กรกำหนดกติกา

## สิทธิ์และความโปร่งใส

เพิ่ม `support.recognition.award` สำหรับผู้ดูแลที่ได้รับมอบหมายให้ประเมิน และ `support.recognition.adjust` สำหรับ Support Admin. ต้องตรวจสิทธิ์เข้าถึง ticket/หมวดร่วมด้วยทุกครั้ง การเป็น assignee เพียงอย่างเดียวไม่ทำให้มีสิทธิ์มอบคะแนน

ผู้แจ้งที่เป็นผู้ดูแลให้คะแนนเรื่องของตัวเองไม่ได้ ให้ผู้ดูแลอีกคนพิจารณา รวมการปรับคะแนนหลังมอบแล้ว. ไม่อนุญาตให้ระบุ reporterId เองใน request

ผู้แจ้งเห็นคะแนนของตน เกณฑ์ที่ได้รับ ข้อความขอบคุณ ผู้มอบ และวันเวลา ผู้ดูแลเห็นข้อมูลตามขอบเขต support; บุคคลทั่วไปไม่เห็นคะแนนรายบุคคลของผู้อื่น. ข้อความขอบคุณเป็นข้อความที่ผู้แจ้งมองเห็น ห้ามคัดลอก internal note อัตโนมัติ

## การแก้คะแนนและวงจรของเรื่อง

- ส่งซ้ำ/กดซ้ำไม่เพิ่มคะแนนซ้ำ: idempotency key และ unique ticket recognition
- ผู้ดูแลทั่วไปกดมอบซ้ำไม่ได้ หลังบันทึกแสดงสรุปแล้ว; ข้อมูลใหม่ภายหลังใช้การปรับคะแนนโดยผู้มีสิทธิ์ พร้อมเหตุผลและประวัติรุ่นก่อน
- คะแนนต่อ ticket หลังปรับยังอยู่ 0–10 และต้องตรงเกณฑ์ของ policy version; ไม่หักแต้มเรื่องอื่น. เก็บ adjustment delta แยก เช่น 8 → 10 เพิ่มสุทธิ +2 ไม่บันทึก +10 ซ้ำ
- หากมอบผิด การปรับ 8 → 0 มี delta −8 และแจ้งผู้แจ้งด้วยภาษาสุภาพว่า “ปรับคะแนนของเรื่องนี้…” พร้อมเหตุผล ไม่ใช้การหักคะแนนเพื่อลงโทษการรายงานโดยสุจริต
- การเปิดเรื่องใหม่ไม่รีเซ็ต recognition และไม่รับแต้มซ้ำ การปิด/ยกเลิก/เชื่อมเรื่องซ้ำภายหลังไม่ถอนคะแนนอัตโนมัติ หากจำเป็นต้องแก้ไขให้ผู้มีสิทธิ์ทบทวนพร้อมเหตุผล
- ผู้แจ้งขอทบทวนผ่านการสนทนาในเรื่องได้ โดยไม่แก้คะแนนตัวเอง

## หน้าจอ

**ผู้ดูแล — ส่วน “ขอบคุณผู้แจ้ง” ใน ticket detail**

แสดงชื่อผู้แจ้งและเลขเรื่อง → checkbox สามเกณฑ์พร้อมคำอธิบาย → สรุป +N คะแนน → ช่องข้อความขอบคุณ → ตัวอย่างข้อความที่ผู้แจ้งจะเห็น → ปุ่มมอบคะแนนและขอบคุณ. เกณฑ์เริ่มต้นไม่เลือกทั้งหมด และปุ่ม +3/+2 disabled จนเลือกพื้นฐาน. ถ้าถอดพื้นฐานต้องล้างโบนัสด้วย

**ผู้แจ้ง — ส่วน “คำขอบคุณจากทีม”**

แสดง “ได้รับ 8 คะแนนขอบคุณ” เกณฑ์ที่ได้รับ และข้อความจากผู้ดูแล; ถ้าไม่มีคะแนนแสดงข้อความขอบคุณตามปกติ. คะแนนสะสมแสดงในรายการของฉันและมีรายการย้อนหลัง ไม่มีข้อมูลบันทึกภายในปะปน

แบบจำลองเฉพาะส่วนอยู่ที่ `output/support-rating-design.html` ลองเลือกเกณฑ์และดูผลฝั่งผู้แจ้งได้. UI จริงรองรับ TH/EN/JP และเก็บข้อความขอบคุณตามต้นฉบับ

## ข้อมูลและ API ที่เสนอ

- `SupportRecognition`: ticketId (unique), reporterId, evaluatorId, policyVersion, criteria, currentPoints, thankYouMessage, createdAt, updatedAt, version
- `SupportRecognitionEvents`: recognitionId, actorId, eventType, old/new criteria, old/new points, delta, reason, messageSnapshot, createdAt (append-only)
- กรณีรอตรวจสอบยังไม่มี recognition; กรณีขอบคุณโดยไม่มีคะแนนมี recognition ที่ currentPoints=0 จึงแยกสองสถานะได้
- ยอดสะสมทั้งหมด = SUM(currentPoints) ของ recognition ของผู้ใช้; ยอดกิจกรรมรายเดือน = SUM(delta) ตามวันมอบ/ปรับในเดือนนั้น ไม่ใช้ createdAt ของ ticket. หากไม่มีข้อมูลแสดง 0 คะแนนสะสม ไม่สร้างตัวอย่างใน production
- Snapshot policy/คะแนนแต่ละเกณฑ์เมื่อมอบ การปรับ policy ในอนาคตไม่คำนวณคะแนนเก่าย้อนหลัง
- `POST /api/v1/support/tickets/:id/recognition`: criteria + message + ticketVersion + idempotency key; server คำนวณคะแนนและผู้รับเอง ตรวจสถานะอย่างน้อยรับเรื่องแล้วและผ่านเกณฑ์ตรวจสอบตามสิทธิ์
- `POST /api/v1/support/tickets/:id/recognition/adjust`: criteria + message + reason + expectedVersion; ตรวจ `support.recognition.adjust`, scope และห้ามประเมินตัวเอง
- `GET /api/v1/support/tickets/:id/recognition` และ `GET /api/v1/me/support-contributions` แบบ paginated
- การมอบ/ปรับ + event + notification outbox ต้อง atomic; แจ้งเตือนซ้ำจาก retry ถูก deduplicate. โหลดสำเร็จเท่านั้นจึงแสดงว่าได้คะแนน ไม่แสดง success optimistic ขณะ server ยังไม่ยืนยัน

## เกณฑ์ตรวจรับเมื่อพัฒนา

1. ส่งเรื่องสำเร็จแสดงคำขอบคุณ/รอตรวจสอบ ไม่มีคะแนนอัตโนมัติจากจำนวนครั้งส่ง
2. ผู้ดูแลเลือกเกณฑ์ได้คะแนนตรง 5/7/8/10; โบนัสเดี่ยวและ request คะแนนนอกเกณฑ์ถูกปฏิเสธฝั่ง server
3. แจ้งเรื่องเป็นผู้ดูแลเองก็ให้/ปรับคะแนนตนเองไม่ได้; เดา ticket ID ข้ามสิทธิ์แล้วอ่าน/มอบไม่ได้
4. กดมอบซ้ำ/retry/concurrent award ทำให้ยอดเพิ่มครั้งเดียว และแจ้งเตือนครั้งเดียว
5. ขอบคุณโดยไม่มีคะแนนแยกจากรอตรวจสอบ; คะแนนไม่เปลี่ยนสถานะหรือ priority ของ ticket
6. การปรับ 8 → 10 เพิ่มยอดสุทธิ 2; เปิดเรื่องใหม่หรือเปลี่ยน policy ไม่ทำให้คะแนนเดิมเพิ่มซ้ำ
7. ปรับลดพร้อมเหตุผลมี event/notification; ผู้แจ้งเห็นผลแต่ไม่เห็น internal notes
8. การส่งล้มเหลวคงข้อมูลในฟอร์ม ไม่แสดงคะแนนสำเร็จ; ไม่มีการส่งข้อความจริงจากแบบจำลอง

## ขอบเขตเริ่มต้นที่เสนอ

ขอบคุณทันทีหลังส่ง + ผู้ดูแลมอบ 0–10 คะแนนตามเกณฑ์ + กระดิ่ง + ประวัติ/ยอดสะสมของตัวเอง + การปรับพร้อมเหตุผล. เกณฑ์และคะแนนในเอกสารนี้เป็นค่าที่เสนอเพื่อให้ลองพิจารณา ไม่ถือว่าองค์กรรับรองเป็นนโยบายแล้ว
